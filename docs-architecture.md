# Как работает система заказа: от клика до таблицы и уведомления

Это подробное описание всей цепочки. Читать сверху вниз. Раздел 1 объясняет
участников, раздел 2 проходит один заказ по шагам, раздел 3 разбирает, что
происходит при сбоях, раздел 4 задаёт порядок реализации.

---

## 1. Участники системы

```
┌──────────────┐   HTTPS    ┌──────────────────────┐   HTTPS   ┌───────────────┐
│  Браузер     │ ─────────▶ │  VPS: Caddy + Next.js│ ────────▶ │ Google Sheets │
│  клиента     │ ◀───────── │  Function (edge)     │ ◀──────── │ API v4        │
│  Next.js UI  │   JSON     │  app/api/order       │           └───────────────┘
└──────────────┘            │                      │   HTTPS   ┌───────────────┐
                            │                      │ ────────▶ │ Telegram      │
                            │                      │ ◀──────── │ Bot API       │
                            └──────────────────────┘           └───────────────┘
                                                                       │
                                                                       ▼
                                                               ┌───────────────┐
                                                               │ Telegram-чат  │
                                                               │ кондитера     │
                                                               └───────────────┘
```

### 1.1 Браузер клиента (фронтенд)

Статическая страница Next.js. Уже готова. Её задачи:

- провести клиента по 4 шагам формы;
- подсказать цену «на лету» (это только предпросмотр, не финальная цена);
- собрать объект `OrderFormData` из `types/order.ts`;
- отправить его на сервер одним POST-запросом;
- показать экран успеха с номером, который вернул сервер, либо экран ошибки.

Фронтенд **не знает** ни токена Telegram, ни ключа Google. Он общается только
со своим сервером.

### 1.2 Серверный эндпоинт Next.js (бэкенд)

Файл `app/api/order/route.ts`. Работает внутри того же процесса `next start`
на VPS (см. `docs-deploy-vps.md`). Это единственное место, где хранятся
секреты и принимаются решения. Задачи:

- принять запрос, отклонить мусор;
- заново проверить данные (клиенту не верим);
- заново посчитать цену (клиенту не верим);
- присвоить номер заказа и время создания;
- записать в таблицу;
- отправить уведомление;
- ответить браузеру.

Среда: обычный Node.js 20+. Доступно всё, включая `Buffer` и `crypto`.
Библиотеку `googleapis` всё равно не берём: она тяжёлая, а нужен один
`append`. Лимит размера тела запроса задаём сами в Caddy/nginx и в коде.

### 1.3 Google Sheets (база данных)

Обычная таблица. Каждый заказ = одна строка. Кондитер открывает её с телефона,
меняет статус, ставит пометки. Это «истина» о заказах. Доступ сервера к
таблице идёт через **сервис-аккаунт**: технический пользователь Google с
собственным e-mail и приватным ключом. Таблица расшаривается на этот e-mail
так же, как на обычного человека.

### 1.4 Telegram-бот (уведомления)

Бот создаётся через BotFather и получает токен. Сервер вызывает
`https://api.telegram.org/bot<TOKEN>/sendMessage` и передаёт `chat_id`
получателя. В первой версии бот **ничего не читает и не отвечает**: он только
курьер. Нет webhook, нет обработки команд. Получатель: приватная группа, куда
добавлен бот и кондитер.

## 2. Путь одного заказа по шагам

Возьмём конкретный пример: Анна заказывает классический торт 3 кг, начинка
«Красный бархат», декор «Надпись», доставка 14 сентября.

### Шаг 1. Клиент заполняет форму (браузер)

1. Открыла сайт, нажала «Оформить заказ».
2. Шаг 1: выбрала продукт `cake-by-kg`, вес 3. Форма подтянула разрешённые
   начинки через `isFillingAllowedForProduct`.
3. Шаг 2: выбрала начинку. Форма подтянула разрешённые виды декора через
   `getDecorOptionsForProduct`.
4. Шаг 3: выбрала «Надпись», заполнила текст, расположение, цвет.
5. Шаг 4: дата, доставка, адрес, имя, телефон, Instagram, комментарий.
6. На каждом шаге `validateStep` не пускает дальше без обязательных полей.
7. Внизу всё время виден предпросмотр цены: `calculatePrice(formData)`. Для
   Анны это 3 × 3000 = 9 000 ₽, декор «Надпись» без доплаты.

В памяти браузера лежит объект:

```json
{
  "productId": "cake-by-kg",
  "weightKg": 3,
  "filling": "Красный бархат",
  "decor": { "type": "text", "text": "С днём рождения", "position": "по центру", "color": "розовый" },
  "dueDate": "2026-09-14",
  "deliveryType": "delivery",
  "address": "ул. Пример, 5",
  "name": "Анна",
  "phone": "+7 999 123-45-67",
  "instagram": "@anna",
  "comment": "без орехов"
}
```

### Шаг 2. Отправка на сервер (браузер)

Анна нажимает «Отправить заказ». `handleSubmit`:

1. Ещё раз прогоняет `validateAll`. Если ошибка, показывает её и выходит.
2. Переводит кнопку в состояние «Отправляем…» и блокирует её. Это важно:
   двойной клик = два заказа в таблице.
3. Делает запрос:
   ```
   POST /api/order
   Content-Type: application/json
   Body: <объект выше> + { "website": "" }   ← honeypot, см. раздел 3.5
   ```
4. Ждёт ответ. Пока ждёт, ничего не показывает кроме спиннера.

Что фронтенд **не делает**: не генерирует номер заказа, не считает финальную
цену, не пишет в таблицу, не шлёт в Telegram.

### Шаг 3. Приём и проверка (сервер)

Функция получает запрос.

1. **Метод и тип.** Не POST или не JSON → `405`/`400`.
2. **Размер тела.** Больше лимита (например 6 МБ с учётом base64 фото) → `413`.
3. **Парсинг.** `await request.json()`. Ошибка → `400 { ok: false, error: "bad_json" }`.
4. **Honeypot.** Поле `website` не пустое → это бот. Отвечаем `200 { ok: true }`
   и **ничего не делаем**. Спамер думает, что прошёл.
5. **Валидация** через `validateOrderForm` из `lib/validators.ts`. Та же функция,
   что на клиенте. Проверяет:
   - `productId` есть в `config/products.ts`;
   - для `perKg` вес в диапазоне и кратен шагу; для `perItem` количество в
     диапазоне; для `fixed` веса и количества нет;
   - начинка есть в списке и разрешена для продукта;
   - тип декора разрешён для продукта; обязательные поля декора заполнены
     (берутся из `decorOptions[].fields` с `required: true`);
   - `dueDate` парсится и не раньше завтрашнего дня;
   - `name` не пустое, `phone` содержит 10–15 цифр после очистки;
   - при `delivery` адрес не пустой;
   - длины строк ограничены (имя 100, комментарий 1000 и т.д.), чтобы не
     раздуть таблицу и сообщение.

   Ошибки → `422 { ok: false, errors: [...] }`. Фронт показывает их у полей.

### Шаг 4. Обогащение заказа (сервер)

Сервер добавляет то, чему нельзя доверять клиенту.

1. **Цена.** `calculatePrice(order)` из `lib/pricing.ts`. Получает
   `cakePrice`, `decorPrice`, `totalPrice`, `decorQuoted`. Если клиент прислал
   свою сумму, она игнорируется.
2. **Номер заказа.** `generateOrderId(order)` из `lib/order-id.ts`:
   `код продукта + код начинки + 4 случайные цифры`, например `CBH4821`.
   Логика та же, что сейчас в `page.tsx` (`productCodeById`,
   `fillingCodeByName`), просто переехала в общий модуль.
3. **Время создания.** `new Date()` на сервере, форматируется в московское
   время для таблицы, ISO для лога.
4. **Человекочитаемые строки.** Название продукта, название декора, сводка
   деталей декора через `buildDecorSummary`. Всё это считается один раз и
   передаётся и в Sheets, и в Telegram, чтобы они не расходились.

На выходе объект `SavedOrder`:

```ts
{
  ...order,            // исходные поля
  orderId: "CBH4821",
  createdAt: "2026-09-05T10:32:11.000Z",
  createdAtLabel: "05.09.2026 13:32",
  productLabel: "Классический торт 3 кг",
  decorLabel: "Надпись",
  decorDetails: "Текст: С днём рождения; Расположение: по центру; Цвет: розовый",
  cakePrice: 9000,
  decorPrice: 0,
  decorQuoted: false,
  totalPrice: 9000,
  directCode: "ZAKAZCBH4821"
}
```

### Шаг 5. Запись в Google Sheets (сервер → Google)

Файл `lib/server/sheets.ts`, функция `appendOrder(saved)`.

**5a. Получить access token.** Файл `lib/server/google-auth.ts`.

Google не принимает приватный ключ напрямую. Нужно доказать владение ключом,
подписав короткий JWT, и обменять его на временный токен.

1. Собрать заголовок и полезную нагрузку JWT:
   ```
   header  = { "alg": "RS256", "typ": "JWT" }
   payload = {
     "iss": GOOGLE_SERVICE_ACCOUNT_EMAIL,
     "scope": "https://www.googleapis.com/auth/spreadsheets",
     "aud": "https://oauth2.googleapis.com/token",
     "iat": <сейчас, сек>,
     "exp": <сейчас + 3600>
   }
   ```
2. Закодировать обе части в base64url, соединить точкой: `header.payload`.
3. Импортировать `GOOGLE_PRIVATE_KEY` (PEM, PKCS#8) через
   `crypto.subtle.importKey("pkcs8", der, { name: "RSASSA-PKCS1-v1_5", hash: "SHA-256" }, false, ["sign"])`.
   PEM → DER: убрать строки `-----BEGIN/END PRIVATE KEY-----`, склеить,
   `atob`, в `Uint8Array`.
4. Подписать `header.payload`, подпись в base64url, получить
   `header.payload.signature`.
5. `POST https://oauth2.googleapis.com/token` с
   `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<jwt>`.
6. Ответ `{ access_token, expires_in: 3600 }`.

Токен живёт час. Заказов мало, поэтому проще брать новый на каждый заказ, чем
кэшировать. Кэширование можно добавить позже.

**5b. Добавить строку.**

```
POST https://sheets.googleapis.com/v4/spreadsheets/{GOOGLE_SHEETS_ID}/values/Orders!A:T:append
     ?valueInputOption=USER_ENTERED&insertDataOption=INSERT_ROWS
Authorization: Bearer <access_token>
Body: { "values": [[ "05.09.2026 13:32", "CBH4821", "Новый", "Классический торт", "3 кг", ... ]] }
```

- `append` сам находит первую пустую строку, ничего не затирает;
- `USER_ENTERED` означает, что Google распарсит дату и числа как дату и числа,
  а не как текст. Тогда в таблице можно сортировать и суммировать;
- порядок 20 значений в массиве жёстко соответствует колонкам A–T из
  `docs-plan.md`. Маппинг живёт в одной функции `orderToRow(saved)`, и только
  там.

Ответ Google содержит `updates.updatedRange`, например `Orders!A47:T47`. Это
номер строки. Его можно вернуть в лог и вставить в Telegram-сообщение как
ссылку `...#gid=0&range=A47`.

**5c. Результат.** `{ ok: true, range: "Orders!A47:T47" }` либо
`{ ok: false, error: "<текст от Google>" }`. Исключение наружу не летит.

### Шаг 6. Уведомление в Telegram (сервер → Telegram)

Файл `lib/server/telegram.ts`, функция `notifyNewOrder(saved, sheetsResult)`.

1. **Собрать текст.** Формат из `docs-plan.md` раздел 3.2. `parse_mode: "HTML"`.
   Каждое пользовательское поле проходит `escapeHtml`: `&`→`&amp;`, `<`→`&lt;`,
   `>`→`&gt;`. Без этого клиент, написавший в комментарии `<b>`, сломает
   сообщение или Telegram вернёт 400.
2. **Добавить служебное.** Если запись в таблицу не удалась, в конец текста
   добавляется строка `⚠️ В таблицу не записалось: <ошибка>`. Кондитер
   увидит проблему сразу, а не через неделю.
3. **Отправить.**
   - Без референса:
     ```
     POST https://api.telegram.org/bot<TOKEN>/sendMessage
     { "chat_id": TELEGRAM_CHAT_ID, "text": "...", "parse_mode": "HTML",
       "disable_web_page_preview": true }
     ```
   - С референсом: `referenceDataUrl` (base64) → `Blob` → `FormData` с полями
     `chat_id`, `photo`, `caption`, `parse_mode`. Запрос на `sendPhoto`.
     Если текст длиннее 1024 символов (лимит подписи), сначала `sendMessage`
     с текстом, затем `sendPhoto` без подписи.
4. **Результат.** `{ ok: true, messageId }` либо `{ ok: false, error }`.
   Исключение наружу не летит.

### Шаг 7. Ответ браузеру (сервер → браузер)

Сервер собирает итог:

| Sheets | Telegram | HTTP | Ответ |
|---|---|---|---|
| ok | ok | 200 | `{ ok: true, orderId, totalPrice, ... }` |
| ok | fail | 200 | то же + `telegramSent: false` (клиенту не важно) |
| fail | ok | 200 | то же + `sheetsSaved: false` (кондитер уже предупреждён в чате) |
| fail | fail | 502 | `{ ok: false, error: "delivery_failed" }` |

Логика: заказ считается принятым, если хотя бы один канал его донёс до
кондитера. Если оба молчат, заказ потерян, и честнее сказать об этом клиенту.

Ответ 200:

```json
{
  "ok": true,
  "orderId": "CBH4821",
  "directCode": "ZAKAZCBH4821",
  "cakePrice": 9000,
  "decorPrice": 0,
  "decorQuoted": false,
  "totalPrice": 9000,
  "summary": "Торт 3 кг (3000 ₽/кг)"
}
```

### Шаг 8. Экран успеха (браузер)

1. `handleSubmit` получает ответ. `ok: true` → `setSuccess({ orderId,
   totalPrice, summary })` данными **из ответа**, не из локального расчёта.
2. Показывается уже готовый экран: сводка, цена, номер, код для Direct, кнопка
   «Открыть Direct».
3. `ok: false` → экран ошибки: «Не удалось отправить заказ. Напишите нам в
   Direct или попробуйте ещё раз». Кнопки «Повторить» и «Открыть Direct».
   Данные формы **не стираются**, чтобы Анна не заполняла всё заново.

### Шаг 9. Кондитер (после системы)

1. В Telegram приходит сообщение с полным заказом и фото.
2. Открывает таблицу, видит строку 47 со статусом «Новый».
3. Анна пишет в Direct код `ZAKAZCBH4821`. Кондитер находит строку по номеру
   (Ctrl+F в таблице), подтверждает детали, меняет статус на «Подтверждён».
4. Дальше жизненный цикл заказа живёт в таблице: «В работе» → «Готов» →
   «Выдан». Система в этом не участвует.

Полная временная диаграмма:

```
Браузер          Сервер              Google              Telegram
  │  POST /api/order │                   │                    │
  │─────────────────▶│                   │                    │
  │                  │ validate          │                    │
  │                  │ calculatePrice    │                    │
  │                  │ generateOrderId   │                    │
  │                  │  JWT → token      │                    │
  │                  │──────────────────▶│                    │
  │                  │◀──────────────────│ access_token       │
  │                  │  append row       │                    │
  │                  │──────────────────▶│                    │
  │                  │◀──────────────────│ A47:T47            │
  │                  │  sendPhoto/Message│                    │
  │                  │───────────────────┼───────────────────▶│
  │                  │◀──────────────────┼────────────────────│ message_id
  │  200 { orderId } │                   │                    │
  │◀─────────────────│                   │                    │
  │ экран успеха     │                   │                    │
```

Типичное время: 1–3 секунды. Основное время уходит на два запроса к Google.

## 3. Что происходит при сбоях

### 3.1 Клиент закрыл вкладку во время отправки
Сервер всё равно завершит работу. Заказ попадёт в таблицу и Telegram. Клиент
не увидит номер, но напишет в Direct, и кондитер найдёт заказ по имени и дате.

### 3.2 Google вернул 403
Почти всегда: таблица не расшарена на e-mail сервис-аккаунта или ключ не тот.
Заказ уходит в Telegram с пометкой ⚠️. Кондитер вручную вносит строку.
Разработчик проверяет шаринг.

### 3.3 Google вернул 401
Токен не получен: испорчен `GOOGLE_PRIVATE_KEY` (чаще всего переносы строк).
Поведение то же, что в 3.2.

### 3.4 Telegram вернул 400
Обычно: не экранированный HTML в тексте или неверный `chat_id`. Заказ лежит в
таблице. В ответе клиенту `telegramSent: false`. Нужен лист `Log` или логи
Docker (`docker compose logs`), чтобы увидеть это. Рекомендация: писать ошибки Telegram в лист
`Log` той же функцией `append`.

### 3.5 Спам и боты
- Honeypot: скрытое поле `website`. Люди его не видят, боты заполняют.
- Rate limiting: не больше 5 запросов на `/api/order` с одного IP в минуту.
  Делается в Caddy (плагин) или nginx (`limit_req`), либо простым лимитером
  в памяти прямо в эндпоинте.
- Проверка `Origin`: если заголовок не совпадает с доменом сайта → 403.
  Защищает от прямых вызовов через curl с чужого сайта, но не от curl вообще.

### 3.6 Двойная отправка
Кнопка блокируется на время запроса. Дополнительно можно передавать с клиента
`clientRequestId` (uuid, генерируется при открытии формы) и писать его в
таблицу. Дубли по нему видно глазами. Настоящая дедупликация потребовала бы
чтения таблицы перед записью, для первого релиза это лишнее.

### 3.7 Слишком большое фото
Клиент: проверка `file.size > 5 MB` → ошибка у поля, файл не принимается.
Сервер: проверка длины `referenceDataUrl` → 413. Двойная защита.

## 4. Порядок реализации

Принцип: каждый шаг оставляет проект в рабочем состоянии и проверяется
отдельно. Не начинать следующий, пока текущий не прошёл проверку.

### Шаг 0. Подготовка окружения (без кода)

- [x] Создать `.env.local` из `.env.example`. Пока пустой.
- [x] Убедиться, что `npm run build` проходит.
- [x] Правки формы закоммичены в `design_v1` (коммит «website»).
- [x] Убрать `@cloudflare/next-on-pages`, `pages:build`, `runtime = "edge"`.
- [x] `output: "standalone"`, `Dockerfile`, `docker-compose.yml`,
      `docker-compose.local.yml`, `.dockerignore`.
- [x] `.npm-cache`, `tsconfig.tsbuildinfo`, дубль `logo.png` убраны из git.
- [x] Проверить сборку образа: образ 343 МБ, главная и `/api/order` отвечают.

Проверка: `git status` чистый, `npm run dev` работает.

### Шаг 1. Общие модули (клиент + сервер) — сделано

Цель: вынести из `page.tsx` логику, которая нужна и серверу.

- [ ] `lib/validators.ts`: реализовать `validateOrderForm(order)` по списку из
      раздела 2, шаг 3. Возвращает `{ valid, errors: Record<string,string> }`
      в том же формате ключей, что сейчас у `errors` в `page.tsx`
      (`"decor.text"`, `"weightKg"` и т.д.).

## 5. Что исправить до начала разработки (ревизия плана)

### 5.1 Обязательно

1. **Убрать Cloudflare из проекта.** Решение: деплой на свой VPS с оплатой в
   рублях (см. `docs-deploy-vps.md`). Следствия:
   - удалить `@cloudflare/next-on-pages` и скрипт `pages:build` из `package.json`;
   - убрать `runtime = "edge"` из `app/api/order/route.ts`, эндпоинт работает
     в обычном Node.js;
   - в `next.config.mjs` включить `output: "standalone"` для лёгкого Docker-образа;
   - секреты читаются через `process.env` из файла `.env` на сервере;
   - для получения Google-токена можно взять `google-auth-library` (класс `JWT`)
     вместо ручной подписи через Web Crypto: в Node это надёжнее и короче.
     Запись строки всё равно делаем через `fetch`, без `googleapis`;
   - rate limiting делает Caddy/nginx или простой лимитер в самом эндпоинте,
     а не панель Cloudflare.
   Делать это в шаге 0, до любого кода API.

2. **Защита от формул в Sheets.** При `valueInputOption=USER_ENTERED` ячейка,
   начинающаяся с `=`, `+`, `-`, `@`, трактуется как формула. Телефон
   `+7 999…` или Instagram `@anna` сломают ячейку или выполнят формулу.
   В `orderToRow` каждую текстовую ячейку пропускать через `safeCell`:
   если первый символ из этого набора, добавить в начало `'`. Числа и даты
   не трогать.

3. **Сжимать фото на клиенте.** Перед чтением в base64 уменьшить через
   `canvas` до 1600 px по длинной стороне, JPEG качество 0.8. Фото с телефона
   5–8 МБ превращается в 300–600 КБ. Это снимает проблему лимита тела запроса,
   ускоряет отправку с мобильного интернета и укладывается в лимит Telegram.
   Серверная проверка размера остаётся как страховка.

4. **Почистить репозиторий.** В git закоммичена папка `.npm-cache`
   (сотни файлов, меняются при каждом `npm install`), в корне лежит
   `logo.png` на 2 МБ (дубль `public/brand/logo.png`), `tsconfig.tsbuildinfo`
   не в `.gitignore`. Добавить в `.gitignore`, удалить из индекса
   (`git rm -r --cached`), закоммитить. Иначе каждый коммит будет тонуть
   в мусорных диффах.

### 5.2 Желательно, дёшево

5. **Тесты на чистую логику.** Добавить `vitest` и покрыть `validators`,
   `pricing`, `order-id`, `orderToRow`, `escapeHtml`, `safeCell`. Это функции
   без побочных эффектов, тесты пишутся быстро и ловят регрессии цен, которые
   иначе заметит только клиент.

6. **Один повтор для Google.** Запросы за токеном и на append повторять один
   раз при сетевой ошибке или 5xx с паузой 500 мс. Google иногда отдаёт
   кратковременные 503. Один retry убирает большую часть ложных ⚠️.

7. **Лимит общей длины сообщения Telegram.** Лимит 4096 символов. При
   ограничениях на поля (комментарий 1000, детали декора 1000, адрес 300)
   сумма укладывается, но `formatOrderMessage` должен обрезать текст с `…`
   на всякий случай.

### 5.3 Альтернатива, которую стоит знать

**Google Apps Script вместо своего бэкенда.** Скрипт, привязанный к таблице,
публикуется как web app и принимает POST. Он пишет в таблицу нативно
(`sheet.appendRow`) без сервис-аккаунта и JWT, и сам вызывает Telegram через
`UrlFetchApp`. Свой сервер тогда нужен только для статики.

| | Своя функция (план) | Apps Script |
|---|---|---|
| Авторизация в Sheets | JWT + Web Crypto, самая сложная часть плана | нет, скрипт живёт в таблице |
| Время ответа | 1–3 с | 2–5 с, холодный старт |
| Валидация и цена | общий код с фронтом | дублировать на JS без типов |
| Секреты | `.env` на сервере | Script Properties |
| Деплой | git push | кнопка «Deploy» руками, новая версия каждый раз |
| CORS | свой домен, проблем нет | нужен `text/plain` и `redirect: follow` |

Рекомендация: остаться на своей функции. Общий код валидации и цены с фронтом
важнее, чем экономия на JWT, а JWT пишется один раз и больше не трогается.
Apps Script имеет смысл, если сложность с сервис-аккаунтом станет блокером.

### 5.4 Что в плане правильно и менять не надо

- Сервер пересчитывает цену и генерирует номер. Без этого сумму можно подменить.
- Sheets и Telegram независимы, заказ выживает при падении одного канала.
- Бот без webhook в первой версии. Входящие обновления добавляют секрет
  webhook, разбор update и ещё один эндпоинт: всё это не нужно для запуска.
- Ручной REST к Sheets вместо `googleapis`. Даже в Node runtime библиотека
  тяжёлая и тянет десятки зависимостей ради одного `append`.
- Порядок шагов: сначала контракт фронт–сервер без внешних сервисов, потом
  Sheets, потом Telegram. Каждый шаг проверяется отдельно.
